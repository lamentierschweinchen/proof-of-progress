## Since the last digest

- **No new releases.** Every tag on the version map is unchanged from yesterday.
- **`mx-chain-go` [#8011](https://github.com/multiversx/mx-chain-go/pull/8011)** "fix epoch change propose rewards epoch" (open, `AdoAdoAdo`) — opened 21:06 UTC Sep 11, single commit. Adds a new enable-epoch flag, `FixEpochChangeProposedCurrentEpochFlag` (the repo's default `cmd/node/config/enableEpochs.toml` sets it to epoch 3, one epoch after the default `SupernovaEnableEpoch=2` — this is the repo's shipped default config, not confirmed as mainnet's actual activation number, which lives separately in `mx-chain-mainnet-config` and hasn't been touched yet). The fix itself: `BlockChainHookImpl.CurrentEpoch()` previously always returned `bh.currentHdr.GetEpoch()`. Once the flag is active, if the current header is a Supernova V3 meta header that `IsEpochChangeProposed()`, the hook now returns `currentEpoch + 1` (the epoch being prepared) instead of the stale current epoch. Test changes touch `vm/systemSmartContracts/delegation_test.go` and `staking_test.go` — i.e., staking/delegation system contracts were computing against the wrong epoch during epoch-change-proposed blocks. `sasurobert` approved at 21:27 UTC, 21 minutes after the PR opened — his first review/commit activity since the three config-PR reviews two digests ago, and a notably fast turnaround for a staking-critical fix.
- **`mx-chain-proxy-go` [#522](https://github.com/multiversx/mx-chain-proxy-go/pull/522)** "temporary stop staking related txs until fixed" (open, `AdoAdoAdo`) — landed 22:38 UTC, roughly 70 minutes after #8011's approval. New `delegationOperationsGuard`: `SendTransaction` and `SendMultipleTransactions` now reject (503, `ErrDelegationOperationsUnavailable`) any tx whose function selector is `claimRewards`/`delegate`/`reDelegateRewards`/`unDelegate`/`withdraw` addressed to a deployed delegation contract, or `claimMulti`/`mergeValidatorToDelegationSameOwner`/`mergeValidatorToDelegationWithWhitelist`/`reDelegateMulti` addressed to the delegation manager SC. `SendMultipleTransactions` rejects the whole batch atomically if any one tx is blocked, without contacting observers (`getObserversCalled` stays false in the test). Other delegation-contract operations (e.g. `stakeNodes`, `createNewDelegationContract`) and identically-named functions sent to non-delegation contracts are explicitly unaffected — confirmed by the accompanying test cases. Read together with #8011, this is a chain-level fix paired with a same-night proxy-level stopgap for the affected transaction types while the fix is still in review.
- **`mx-api-service` [#1637](https://github.com/multiversx/mx-api-service/pull/1637)** "Check tokens created within all tokens processing time window" (open, `stefangutica`) — the sixth PR in the ongoing API-consistency run. Applies the same fix pattern as #1635 (meta-ESDT collections) to newly issued fungible tokens: the `getAllTokensRaw` cache-warmer pass can take tens of seconds, during which a token created mid-pass gets overwritten out of the cache by the warmer's own stale snapshot. The fix adds a second, narrower pass after the main one that only reprocesses tokens missing from the initial list, shrinking the race window from "tens of seconds" to "a few seconds."
- **Org-wide sweep**: nothing outside the watchlist worth flagging.
